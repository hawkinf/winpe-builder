## Visão geral
Programa GUI em C# que baixa/obtém os arquivos essenciais do WinPE (x86/x64), injeta arquivos do usuário e gera a ISO.

## Estrutura de pastas
src/WinPEBuilder.sln

  WinPEBuilder.App/    – GUI WPF (net10.0-windows); só apresentação, chama o Core
  WinPEBuilder.Tests/  – testes xUnit do Core
scripts/ (PowerShell/UIA PEBakery, check-handoff), config/, tools/, build/, output/ (binários ignorados pelo git)

## Armadilhas conhecidas
- (coisas que já custaram tempo a alguém)
- DandISetEnv.bat lê o registro (KitsRoot10) e roda WimMountAdkSetup; por isso NÃO o usamos: AdkInstall.BuildEnvironment() monta WinPERoot/OSCDImgRoot/DISMRoot/PATH e funciona também para ADK em pasta privada.
- O ADK atual (24H2/26100) não tem WinPE x86; só o ADK Windows 10 2004 (linkid 2120254 + add-on 2120253) tem.
- Core/Processes: CommandSpec (inclui Cmd() p/ .cmd com aspas corretas e Quote()) + ProcessRunner (saída na codepage OEM, stdin fechado p/ nunca travar em "Y/N"). Core/AppPaths: tudo em %LOCALAPPDATA%\WinPEBuilder (downloads, adk\<id>, work\<arch>).
- AdkInstaller só aceita instaladores com assinatura Microsoft válida; exit code 3010 = sucesso (reboot).
- App usa manifest requireAdministrator (DISM exige); `dotnet run` abre pedido de UAC.
- Core/Build/WinPeBuildService: pipeline em etapas (PlanSteps). Fonte ADK = copype; fonte ISO = Mount-DiskImage + cópia de boot/efi/bootmgr + `dism /Export-Image /SourceIndex:1 /Bootable`. Se algo falhar/cancelar com a imagem montada, o `finally` faz `/Unmount-Image /Discard`.
- Segurança: a pasta de trabalho só é apagada se estiver DENTRO de allowedWorkRoot (AppPaths.Root); caso contrário BuildException.
- Pacotes opcionais: OptionalComponents.All tem ordem = ordem de instalação; Resolve() inclui dependências.
- Armadilha: arquivos copiados de ISO são somente leitura — FileSystemHelper limpa o atributo (senão Directory.Delete falha).
- Arquivos do usuário: OnIso (padrão recomendado) copia p/ `media\Arquivos` e o startnet.cmd procura em C..Z o `Arquivos\.winpe-files` e faz `subst Z:`; InsideImage copia p/ `X:\Arquivos` (RAM, limite 1 GB). Letra Z (não P): em PCs reais P/outras já são comuns; subst falho é silenciado e %ARQUIVOS% sempre vale. `startup.cmd` na pasta roda automaticamente.
- ISO: `oscdimg -m -o -u2 -udfver102 -l<label> -bootdata:2#p0,e,b"<etfsboot.com>"#pEF,e,b"<efisys[_noprompt].bin>" <media> <iso>` (igual ao MakeWinPEMedia; UDF suporta arquivos >4 GB). BootFiles.Resolve procura em fwfiles → Deployment Tools\<arq>\Oscdimg → mídia da ISO de origem, sempre da arquitetura de destino.
- UsbMediaWriter chama `MakeWinPEMedia /UFD /F` (FORMATA o pendrive): só aceita discos removíveis prontos que não sejam o do Windows, revalida a letra na hora e exige o WinPE já gerado na pasta de trabalho. A GUI deve confirmar com letra+nome+tamanho.
- GUI (App): MainWindow = code-behind fino; toda lógica fica no Core. `RunOperationAsync` centraliza log em arquivo (%LOCALAPPDATA%\WinPEBuilder\logs), cancelamento e erros amigáveis (BuildException mostra a mensagem; outras exceções vão só pro log + mensagem genérica). Fechar a janela durante uma operação cancela, ESPERA o `finally` desmontar o WIM (/Discard) e só então fecha.
- UsbWindow exige digitar a letra do pendrive para habilitar "Formatar e gravar". Botão de pendrive só habilita após uma geração bem-sucedida na sessão.
- Teste de fumaça sem admin: `dotnet build src/WinPEBuilder.App -p:ApplicationManifest= -o <pasta fora do repo>` gera uma variante sem o manifesto requireAdministrator.
- Programas (Core/Programs): ProgramEntry (nome, categoria, exe de origem, CopyFolder, desktop/menu) → ProgramStaging copia p/ `Arquivos\Programas\<id>\` e grava `Arquivos\programs.json` (v1, UTF-8 sem BOM; `exe` é relativo à pasta Arquivos, com `\`). O launcher resolve contra %ARQUIVOS%. Com programas e sem pasta de arquivos o modo vira OnIso (BuildOptions.EffectiveFilesMode).
- Segurança da cópia: CopyFolder recusa raiz de unidade, Windows, System32, Program Files, perfil do usuário, Desktop/Documentos/Downloads e qualquer pasta que CONTENHA uma delas (ProgramEntry.IsProtectedFolder). (Pastas de origem iguais são copiadas uma vez só — ver StageFolderName abaixo.)
- Launcher (`src/WinPEBuilder.Launcher`, net48 WinForms, sem dependências; exe `WinPELauncher.exe`): `Model/LauncherManifest.cs` (DataContractJsonSerializer — net48 não tem System.Text.Json; parse tolerante, `ResolveExe` recusa caminho fora de Arquivos, agrupamento por categoria, `FindFilesRoot`: %ARQUIVOS% e depois C..Z) é compilado TAMBÉM no projeto de testes (link) para testar o contrato Core→launcher. UI: `DesktopForm` (tela cheia atrás de tudo, ListView de ícones; Alt+F4 bloqueado), `TaskbarForm` (TopMost, Iniciar/tarefas/relógio; menu por categoria + cmd/PowerShell + wpeutil reboot/shutdown), `Native` (reserva a área de trabalho via SPI_SETWORKAREA e restaura ao sair), `ProgramRunner` (inicia, ícones, AppLog em %TEMP%). `--preview` = janela normal, não mexe na área de trabalho e não reinicia/desliga (use para testar no Windows comum).
- Injeção (A4): `BuildOptions.InstallLauncher` = há programas + origem ADK + `LauncherExePath`; então `EffectiveComponents` acrescenta WinPE-NetFx (+WMI por dependência), uma etapa copia o exe para `mount\Windows\System32` e o `startnet.cmd` (`StartnetScript.Build(mode, launcher:true)`) faz `start "" "%SystemRoot%\System32\WinPELauncher.exe"` DEPOIS de definir %ARQUIVOS% e ANTES do startup.cmd do usuário. O App compila o launcher junto (ProjectReference ReferenceOutputAssembly=false + alvo CopyLauncher) em `launcher\` ao lado do WinPEBuilder.exe. Origem ISO: sem .NET → só copia os programas e loga aviso.
- App: `ProgramWindow` (adicionar/editar; sugere o nome pelo ProductName do exe; tamanho calculado em segundo plano) e grupo 6 na MainWindow; programas persistem em `UserSettings.Programs` (settings.json).
- Armadilha de teste visual: o app pede admin; para smoke test use `$env:__COMPAT_LAYER='RunAsInvoker'` e capture SÓ a janela (PrintWindow), nunca a tela inteira. settings.json só é gravado ao FECHAR (matar o processo não grava).
- Publicação (`dotnet publish` do App, qualquer -r, com ou sem self-contained/single-file): o ProjectReference ao Launcher usa `GlobalPropertiesToRemove` (senão TargetFramework/RuntimeIdentifier do app vazam para o net48 → NETSDK1005/1047); o Launcher declara `RuntimeIdentifiers=win-x86;win-x64` (restore vindo do App usa o RID do app, o build usa o padrão win-x86); o alvo `PublishLauncher` põe `launcher\WinPELauncher.exe` na pasta publicada com `ExcludeFromSingleFile` (sem isso o bundler descarta o arquivo). Sem o launcher ao lado do .exe o build com programas falha na validação ("launcher não encontrado").
- Pasta de programas (Core/Programs): `ProgramEntry.SourceRoot` (raiz escolhida em "Adicionar pasta"; o exe pode estar numa subpasta; só vale com CopyFolder) e `DesktopFolder` (nome da pasta da área de trabalho). `ProgramStaging.StageFolderName` faz programas com CopyFolder e mesma SourceFolder compartilharem UMA cópia (subpasta = id do primeiro; resolve a antiga armadilha da cópia dupla); `RelativeExe(all, p)` usa o caminho relativo à raiz; `TotalBytes` conta a pasta compartilhada uma vez. `ProgramScanner.FindExecutables` (profundidade 3, máx. 300, ignora unins*/vc_redist*, não segue reparse points). Manifesto v1 ganhou o campo opcional `folder` (launcher antigo/novo ignoram o que não conhecem). Launcher: `ManifestReader.DesktopFolders`, `FolderIcon` (ícone desenhado em código) e `FolderForm` (janela com os programas da pasta). App: `FolderImportWindow` (DataGrid com ExeRow) e campo "Pasta no desktop" no ProgramWindow.
- Teste visual de janela WPF sem automatizar diálogos nativos: projeto descartável fora do repo referenciando WinPEBuilder.dll, instalar DispatcherSynchronizationContext, chamar o método privado por reflection e renderizar com RenderTargetBitmap (controles do XAML são internal: use FindName).
- Editor visual: `Core/Programs/DesktopLayout.cs` (grade: CellSize 80, 12x9 = tela 1024x768 menos barra; `DesktopSlot`, `DesktopItem`, `Items()` = pastas primeiro e depois soltos, ambos alfabéticos como no launcher; `Normalize` mantém posições válidas, poda chaves mortas, posiciona o resto coluna a coluna; `StartMenuModel`) e `DesignerModel.cs` (TODA a lógica: MoveTo troca se ocupada, MoveIntoFolder, TakeOutOfFolder, RenameFolder, DissolveFolder, Add/Replace/Remove, AutoArrange, Dirty; trabalha sobre CÓPIA — descartar = não usar o resultado). Chaves do layout: `p:<id>` e `f:<NOME EM MAIÚSCULAS>` (mesma regra em Core e launcher; teste garante). Persistência: `UserSettings.DesktopLayout` → `BuildOptions.DesktopLayout` → campo opcional `layout` do programs.json (só emitido se não vazio). Launcher: `ManifestReader.PixelPositions` (null se faltar posição de algum ícone → arrumação automática para todos) e `DesktopForm.ApplyLayout` com `AutoArrange=false`.
- App: `DesignerWindow` (Viewbox 1024x768; ícones = Border com handlers de mouse; arrastar ícone com captura + destaque da célula; arrastar da lista/pasta/Explorer via DragDrop com formatos `wpb-program`/`wpb-from-folder`/FileDrop; menu Iniciar = ContextMenu; `Saved` indica gravar), `ShellIcon` (SHGetFileInfo → ImageSource, ícone de pasta desenhado), `InputWindow`. ProgramWindow/FolderImportWindow aceitam caminho inicial (soltar do Explorer).
- ARMADILHA (launcher): `ListViewItem.Position` é ignorado se o ListView ainda não tem handle — aplicar o layout em `OnShown`, não no construtor.
- Teste de UI real sem tocar no resto da máquina: projeto descartável referenciando WinPEBuilder.dll, janela Topmost em posição fixa, `SetCursorPos`+`mouse_event` para arrastar de verdade, ler o `_model` por reflection. NÃO capturar a tela inteira (CopyFromScreen) — use RenderTargetBitmap/PrintWindow só da janela.
- Subpastas: nao existem sozinhas, sao derivadas de `ProgramEntry.DesktopFolder` com caminho `A/B` (`Core/Programs/FolderPath.cs`: Normalize/Key/Top/Parent/Replace; limites 4 niveis, 40 por nivel, 120 total). So as de primeiro nivel viram icone na grade (chave `f:TOPO`); o resto aparece dentro da janela da pasta. `DesktopLayoutHelper.FolderContents` (subpastas diretas + programas diretos) e `ManifestReader.FolderContents` no launcher TEM de dar o mesmo resultado (teste de paridade). Operacoes no `DesignerModel` trocam prefixo de caminho (rename/move/dissolve) e `Refresh` poda o layout. Launcher: `FolderForm` navega com `FolderNav` (item `..` = pai) e o titulo mostra `A > B`. Manifesto antigo (pasta plana) continua valido.
- Papel de parede: `Core/Programs/Wallpaper.cs` (`WallpaperSettings`: ImagePath/Mode/Color; Validate) → `UserSettings.Wallpaper` → `BuildOptions.Wallpaper` → `ProgramStaging` copia a imagem para `Arquivos\wallpaper.<ext>` e grava o bloco opcional `wallpaper {file, mode, color}` no manifesto (omitido se for o padrão). `Launcher/Model/WallpaperGeometry.cs` (retângulos de cada modo, cor, modo normalizado) é COMPILADO NO LAUNCHER, NO APP E NOS TESTES: preview e WinPE usam a mesma conta. Launcher: `DesktopIcon` (Control com fundo transparente desenhado por nós — o ListView não suporta fundo transparente, por isso foi abandonado) + `DesktopForm` (OnPaintBackground desenha o bitmap já no tamanho da tela; `PlaceIcons` coloca na grade visível e realoca o que cair fora; nunca esconde ícone). App: `WallpaperRenderer` (DrawingVisual → RenderTargetBitmap, cache por caminho+data), `WallpaperWindow` (preview exato), `DesignerModel.Wallpaper/SetWallpaper` (entra no Gravar/Descartar). Armadilhas: GDI+ lança OutOfMemoryException para arquivo que não é imagem (tratado); Image.FromFile trava o arquivo (por isso copia para Bitmap via stream).
- Shell do WinPE: por padrao o winpeshl.exe roda `cmd.exe /k startnet.cmd` (o prompt na tela) e REINICIA o PC quando o shell termina. Com launcher o app grava `Windows\System32\winpeshl.ini` (`StartnetScript.BuildWinpeshlIni`): `[LaunchApps]` = startnet.cmd (cmd /c: wpeinit, subst Z:, startup.cmd em janela propria) → WinPELauncher.exe (shell, fica aberto) → cmd.exe (reserva: so aparece se o launcher terminar, evita loop de reinicio). O winpeshl executa os itens em SEQUENCIA e espera cada um (testado no QEMU). Sem launcher nada muda (shell padrao). O launcher nao pode ser fechado pelo usuario (Alt+F4 bloqueado); Reiniciar/Desligar ficam no menu Iniciar (wpeutil).
- Arquitetura dos programas: o WinPE amd64 NAO executa .exe de 32 bits (sem WOW64 completo: nao ha wow64.dll nem os controles comuns x86 no WinSxS; o Windows so diz "side-by-side configuration is incorrect"). `Launcher/Model/PeInfo.cs` (le so o cabecalho PE; COMPARTILHADO: compilado no launcher e no Core via link) + `Core/Programs/ProgramCompatibility.cs` (Check/Warnings/Label). Usos: `BuildOptions.CompatibilityWarnings` (log `Aviso:` e confirmacao na GUI antes de gerar; NAO bloqueia), coluna Arq. na lista, icone com triangulo no editor (`DesignerWindow(architecture)`), confirmacao no ProgramWindow, linhas desmarcadas no FolderImportWindow, e `ProgramRunner.Explain` no launcher (mensagem clara quando o CreateProcess falha). Teste de campo: QEMU + ISO secundaria com script, digitando no prompt via `sendkey` (teclado ABNT2: `\` = tecla `less`, `:` = shift-slash).
- Configuracao do usuario: `UserSettings` e o MESMO objeto do `settings.json` automatico (Load tolerante, nunca lanca) e dos arquivos `.winpe.json` que o usuario grava/abre (`TryRead` ESTRITO com mensagem de erro; limite 5 MB; `FormatVersion` = 1, versao maior e recusada). A GUI valida o arquivo ANTES de mexer na tela, confirma a substituicao e depois lista `FindMissingFiles()` (caminhos sao absolutos: configuracao levada a outro PC avisa o que falta). Novo campo em UserSettings => atualizar CollectSettings/ApplySettings da MainWindow e os testes de ida e volta (ConfigFileTests.SaveThenRead_RestoresEverything).
